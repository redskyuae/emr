# The Protected Area Boots Behind a Branded Splash Gate

Entering the protected area depends on the Current User (`/api/v1/me`): today the sidebar reads it for the Tenant name, and it will soon drive the entire navigation menu from the Current User's Effective Permissions. Previously the shell rendered immediately and the sidebar filled in `/me` data behind a small inline skeleton, which means that once the menu becomes permission-driven a user would briefly see an empty or wrong menu before `/me` resolved. We are introducing a single app-boot gate in front of the whole shell so that nothing permission-dependent paints until the Current User is known.

The gate is an in-place client component (`AppShellGate` + a presentational `AppSplash`) that the server `app/(protected)/layout.tsx` renders around the shell (sidebar, topbar, and page content). It is deliberately **not** a separate `/loading` route and it performs **no redirect**: the user navigates straight to their destination URL, the splash is a full-viewport overlay on top of that route, and when the Current User resolves the overlay fades and reveals the shell. The URL never changes, so deep-links and refresh work unchanged. The server layout keeps its existing pre-gate responsibilities — no Session redirects to `/login`, and a not-yet-onboarded Tenant redirects to `/onboarding` — and the gate only governs the client-side wait for `/me`.

The gate is a small phase state machine (`loading` → `fading` → `ready`, or `error`) rather than a `<Suspense>` boundary, because the behavior we want is imperative: the splash shows for a **minimum of ~800ms with a ~200ms fade-out**, and stays longer if `/me` is slower. It reads the existing `useCurrentUserQuery` cache, so the sidebar's own `useCurrentUserQuery` is already warm when the shell mounts and paints with no extra fetch. The splash fires **once per app entry** — fresh load, hard refresh, or return-from-login — and, because the Current User is cached for the tab afterwards, intra-app navigation shows no splash at all. The per-route `loader.tsx` skeletons are a separate, untouched layer: the splash is the app-boot layer, the skeletons are the per-page layer, and they stack rather than replace each other. Visually the splash reuses the existing `LogoMark` as a temporary brand mark, animates a gentle logo fade/pulse (Fluent-inspired, themed from `app/globals.css`), and fully honors `prefers-reduced-motion` by dropping the pulse and the fade.

The central trade-off is that we chose a **guaranteed brand moment over the fastest possible paint**. The rejected alternative was to prefetch `/me` on the server in the layout (which already holds the Session), dehydrate it into React Query, and render a permission-correct shell on the very first paint with no splash — strictly faster and flicker-free. We rejected it because the goal here is the deliberate, Outlook-style boot moment, which an instant server-rendered shell would erase. The minimum-duration hold means adding up to ~650ms of intentional delay on fast connections; this is acceptable precisely because the cost is paid once per app entry (once per shift for clinical staff), not on every navigation. If that calculus ever changes, the honest move is to reverse this decision toward server prefetch rather than to shorten the hold into a flicker.

Failure has a defined screen so the gate is exhaustive and never an infinite spinner. A **401 or 403** from `/me` means the Session is gone or unusable, so the gate **redirects to `/login`**. A **500, network, or offline** failure keeps the user in the branded frame and shows an **error state with a Retry** action that refetches `/me`; React Query auto-retries a couple of times first so transient blips self-heal before the error surface appears. We deliberately do **not** send transient failures to `/login`, because a login page cannot render or authenticate under the same network fault and would only look broken.
