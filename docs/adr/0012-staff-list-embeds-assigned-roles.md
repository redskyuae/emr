# Staff List Embeds Assigned Roles and Supports Role/Status Filters

The Staff directory screen (`/identity-access/users`) shows each Staff member's assigned Roles and lets admins filter the list by Role and by active/inactive status. The Staff list query (`GET /api/v1/users`) previously returned bare `Staff` rows with no Roles — Roles were only reachable through the per-Staff endpoint `GET /api/v1/users/[id]/roles`. We are extending the list response to embed a lean `roles: { id, name }[]` on each row, and adding two server-side filter params, `roleId` and `status` (mapping to `isActive`; omitted = all), alongside the existing `query`/`page`/`limit`.

We chose embedding over the two alternatives. Fetching `/users/[id]/roles` once per visible row (N+1) would mean N requests per page, would not survive pagination, and could not power a server-side Role filter. Dropping Roles from the directory entirely would lose the single most important column and the Role filter. Embedding a minimal `{ id, name }` per row keeps the list a single request, makes the Role column free, and lets `roleId` filter at the database via a join — at the cost of a slightly wider list contract and a join in the Staff repository.

This is non-obvious because dedicated Role endpoints already exist, so a future reader could reasonably assume the list should stay role-free and "fix" the redundancy or reach for N+1. The embedded shape is intentionally lean (`id` + `name`, not the full `Role`) to keep the contract small; richer Role data still comes from `/roles` and `/users/[id]/roles`. Reversing the decision means changing the list response type (`Paginated<StaffWithRoles>`) and every client that reads it, so new directory features should build on the embedded shape rather than reintroducing per-row Role fetches.
