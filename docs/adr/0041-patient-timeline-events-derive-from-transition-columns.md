# Patient Timeline Events Derive From Transition Columns

The Patient Timeline is a reverse-chronological feed of everything that happened to one Patient — Bookings, Visits, Admissions, Bed Transfers, Invoices, Payments, Visit Documents, and signed Clinical Notes — merged into a single infinite-scrolling list. Each Timeline Event is one **lifecycle transition**, not one record: a Visit that was checked in, seen, and completed contributes three Timeline Events at three points on the feed, each linking back to the same `/visits/[id]` page.

Timeline Events are **derived at read time from the transition timestamp columns already stored on the source records**. They are never persisted. The alternative — a materialized `patient_timeline_event` table written by every command as it acts — was rejected for v1.

The read is a single repository function issuing one `UNION ALL` with one branch per transition. Each branch projects to a common shape (`occurredAt`, `sourceType`, `sourceId`, `eventType`, `reference`, plus a small display payload), filters on `tenant_id`, `patient_id`, `is_deleted = false`, and `<transition column> IS NOT NULL`, and the whole union is ordered `occurred_at DESC, source_type DESC, source_id DESC` with a keyset cursor. This gives exact pagination in one round trip: a cursor identifies a point in the merged ordering rather than an offset into any one source, so no source can drift or duplicate as the user scrolls. Multi-transition records need no special handling — each transition is simply its own branch. `visit_document` has no `patient_id` and reaches the Patient through a join on `visit`.

Deriving rather than materializing means:

- **It works on existing data immediately.** No backfill migration, and every Visit, Admission, and Invoice already in the database appears in the feed on the day the tab ships.
- **There is no dual-write path to forget.** A materialized table requires every command in six modules to write an event; one missed write leaves a silent, permanent hole in a patient's history that no test would catch. Derivation cannot drift from the records it reads because it _is_ the records.
- **A Timeline Event can only exist where a timestamp column exists.** This is the real cost, and it is a hard constraint, not a detail. Two gaps were closed in the same change to make the model whole: `appointment.cancelledAt` and `patient.deactivatedAt` / `patient.reactivatedAt` were added, because both transitions previously left no trace beyond `modifiedOn`, which any unrelated edit clobbers. Rows predating those columns hold `NULL` and simply do not appear — a pre-existing cancellation is invisible rather than wrongly timestamped.
- **Anything without a business timestamp is out of scope by construction.** "Appointment rescheduled" and field-level edits cannot be Timeline Events. Adding them means adding columns, not adding rows.

Timeline Events are returned as **UTC instants only**. The client converts and groups them in the viewer's browser time zone; the server sends no precomputed local date. This is a deliberate departure from ADR 0026, which gives the Tenant Time Zone authority over operational time — that ADR governs _decisions_ the server makes (whether a DoctorSlot has passed, which day an Appointment is booked into), whereas the Timeline only _displays_ instants that are already settled. The consequence is that day headers follow the viewer's device, so a discharge near local midnight can file under an adjacent date for a viewer in another zone. Accepted: it keeps timezone handling entirely in the presentation layer and matches how the rest of the app already formats dates.

The query also required `(tenant_id, patient_id)` indexes on `visit`, `admission`, `appointment`, and `clinical_note`; `invoice` and `payment` already had theirs. Chart records — Allergies, Problems, Medications, Vital Signs — are deliberately **excluded**. Their dates (`onsetDate`, `notedOn`, `startDate`) are clinical facts, not system events, and would place a problem with a 2019 onset years down a feed whose every other entry means "this happened at the hospital." Vital Signs would additionally drown the feed during an Admission. The Patient Chart tab already owns all four.

Revisit this decision if the Timeline grows toward a genuine audit trail — actor identity, request origin, field-level diffs. None of that lives in business columns, and at that point a real event table (likely shared with the audit log, which currently exists only as a mocked page) becomes the right substrate. Migrating then is a backfill plus a write-path change across six modules; that cost is the price of not paying it now.
