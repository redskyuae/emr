# Product Analytics Is Allow-Listed and Free of Patient Data

The vendor's product and customer-success team records how staff use the EMR as **Analytics Events** in PostHog Cloud (EU region). This is the project's first rule on sending data to a third party, and it is deliberately narrow: analytics exists to understand product usage, not to report to hospitals and not to audit who did what to which Patient.

**What may be sent.** Fixed system categories (Booking Path, Visit Status, Payment Method), Master codes that classify workflow (AppointmentMode, VisitType), yes/no flags, counts and whole-number durations. A signed-in user is the internal user id with Role codes and Tenant Owner or Admin status; a Tenant is its id, name, slug and time zone. **What is never sent:** anything that identifies a Patient or describes their care, any record identifier (Patient id; Appointment, Visit, Admission, Invoice or Payment id or number), money amounts, anything a user typed (search terms, reasons, remarks, error text), and Staff names, emails, phones or staff codes. Page addresses are cleaned before sending: every id segment becomes `:id` and the query string is dropped, for the current address, the referrer and the initial address and referrer PostHog keeps on the person.

**The catalogue is an allow-list.** Every event and every property is declared once in `lib/analytics/catalogue.ts` with the kind of value it may hold (`enum`, `code`, `count`, `boolean`, ...). The typed capture helpers accept only declared events, and at run time the browser's PostHog before-send hook drops any event or property that is not declared, or whose value does not fit its kind. So a free-text value cannot pass as an enum or a code, and adding an event is a reviewed change to one file. A unit test fails if a non-boolean property's name looks like Patient data, a record id, money or text.

**Outcomes are recorded by the server, steps by the browser.** Only the server knows that an action succeeded, so business outcomes (`appointment_booked`, `visit_completed`) are recorded from the route handler's success branch, after the response, and exactly once. The browser records page views, identity and in-workflow steps (started, abandoned, rejected), and never records an outcome again.

**Configuration is passed from the server.** `ANALYTICS_ENABLED`, `POSTHOG_PROJECT_KEY` and `POSTHOG_HOST` are read on the server and handed to the client provider as props, as the brand variant is; the project has no `NEXT_PUBLIC_` variables, and the switch must be one setting per deployment. With it off, PostHog is never loaded and nothing is sent. There is no per-Tenant setting and no consent prompt for staff.

**Same-origin ingestion without the session cookie.** The browser sends events to `/relay` on the app's own origin, so staff browsers make no third-party analytics requests. A Next rewrite would forward the browser's headers, including the BetterAuth session cookie and a Referer holding the full page address, so a route handler (`app/relay/[...path]/route.ts`) builds the upstream request from an allow-list of headers instead. `proxy.ts` does not run on that path, so anonymous login and signup events are not redirected to `/login`.

**Nothing stored before sign-in.** PostHog keeps its state in memory until the user signs in, then switches to `localStorage`; signing out, or a Session ending, records `signed_out`, resets identity and clears what was stored. Session replay, autocapture, heatmaps, surveys, exception capture and performance capture are off, because each copies on-screen text or addresses.

**Analytics never gets in the way.** Every capture is wrapped so a PostHog failure is silent, the browser SDK loads lazily, and server sends run after the response.

**Considered.** PostHog's `cookieless_mode` was rejected for the pre-sign-in rule: it must also be enabled in the project and applies to the whole session, where in-memory persistence switches cleanly at sign-in. Initialising from `instrumentation-client.ts` with public variables, as PostHog's Next guide does, was rejected because the switch must be readable at run time. A deny-list of sensitive property names was rejected in favour of the allow-list: a deny-list fails open the first time someone names a property differently.

**Consequences.** Per-Tenant comparison works best with PostHog's paid Group Analytics; every event also carries `tenant_id` and `tenant_slug` as plain properties so breakdowns work without it. A reload between the login page and the app shell loses the link between the anonymous visitor and the signed-in person, which is accepted. A Content-Security-Policy added later must allow `/relay`. See `docs/analytics.md` for the full rules and how to add an event.
