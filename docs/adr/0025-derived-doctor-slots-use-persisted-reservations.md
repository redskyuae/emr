# Derived Doctor Slots Use Persisted Reservations

DoctorSlots remain derived from DoctorSchedules and DoctorRotas rather than becoming independently stored entities. Appointment creation identifies selected slots by `slotDate` in `DD-MM-YYYY` format, `doctorRotaId`, and ordered `slotTimes` in `HH:mm` format; numeric legacy slot IDs are rejected because the current slot ordinal restarts within every DoctorRota and has no stable database identity.

Date formatting is normalized only at API boundaries. DoctorSchedule storage, repository comparisons, and existing responses remain ISO `YYYY-MM-DD`; DoctorSlot search accepts either ISO or `DD-MM-YYYY` input for compatibility, while Appointment creation uses `DD-MM-YYYY`. Repositories receive ISO dates so chronological comparisons do not depend on display formatting.

Creating an Appointment persists one Appointment Slot Reservation for each selected time in the same transaction as the Appointment. The server validates that the times are generated by the selected DoctorRota for that Doctor and date, are consecutive, and are still available; client-supplied rota names and booking statuses are not trusted. Persisting only the reservations retains schedule derivation while providing a database-enforced concurrency boundary against double booking.

Only DoctorSlots whose start time has not passed may be reserved. Appointment creation rechecks this rule and availability inside the booking transaction rather than relying on an earlier slot-search response.

An active reservation is unique by Tenant, Doctor, date, and time across all DoctorRotas. The DoctorRota identifier is retained for validation and display but deliberately excluded from the uniqueness key, because overlapping rotas must not allow the same Doctor to be booked twice at the same time.

The Appointment also snapshots the validated DoctorRota name at booking time. Clients never submit this value, and later DoctorRota renames or removal do not rewrite historical booking records; the reservation's DoctorRota identifier remains available for identity and audit.

Cancelling or soft-deleting an Appointment releases all of its reservations, while rescheduling releases the old reservations and acquires the replacement reservations in one transaction. Released reservations remain stored for audit but no longer participate in active uniqueness. Completed and No-show Appointments retain their reservations as scheduling history.
