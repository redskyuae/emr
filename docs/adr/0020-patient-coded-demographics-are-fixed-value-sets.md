# Patient Coded Demographics Are Fixed Value Sets, Not Masters

Patient Registration captures several coded demographic values: `gender`, `bloodGroup`, `maritalStatus`, and `govtIdType`. Nearly every other coded value in this system is either a Tenant-scoped Master (AppointmentMode, Asset Status, …) or a Global Reference (Nationality, Language, Religion), so a future reader will reasonably ask why these four are neither. We decided they are **fixed value sets enforced by the Zod schemas and stored as plain `varchar` columns** — not Master tables, not Global Reference tables, and not Postgres enums.

The value sets are globally standardized (gender and marital status follow the HL7 FHIR value sets; blood groups are the eight ABO/Rh types), so per-Tenant configurability adds no domain value while costing three-plus full Master modules, onboarding seeding, and FK joins on every Patient read. Postgres enums were rejected because extending one requires a migration and no existing table in the codebase uses `pgEnum`; with Zod-enforced varchars, adding a value is a code change validated at the API boundary. The trade-off is that the database itself does not reject an out-of-set value written outside the application — acceptable because all writes go through commands that validate first.

Fixed value sets as of this decision: `gender` = male | female | other | unknown; `bloodGroup` = A+ A− B+ B− AB+ AB− O+ O−; `maritalStatus` = single | married | divorced | widowed | other; `govtIdType` = passport | national-id | driving-license | other. If a Tenant ever genuinely needs custom values for one of these, promote that one field to a Master deliberately rather than treating this ADR as forbidding it.
