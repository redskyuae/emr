# Emirates ID Is A Dedicated Patient Attribute, Not An Identity Document

This platform serves the UAE, where the Emirates ID is the de facto patient identifier: it is what a receptionist reads off the card to pull up a returning patient, and what insurance eligibility and claim submission key on. Patient already carried a single generic government ID — a `govtIdType` enum (`passport`, `national-id`, `driving-license`, `other`) paired with a `govtIdNumber`. Emirates ID could have been a fifth value of that enum. It is instead **its own nullable column on `patient`**, sitting beside a separate `patient_identity_document` collection that holds everything else.

The generic pair had one slot, and one slot cannot represent the most common patient in this market. An Indian software engineer living in Dubai holds an Emirates ID _and_ an Indian passport; both are recorded at registration, because eligibility runs off the first and nationality off the second. Adding `emirates-id` to the enum would have meant recording one destroyed the other. It would also have made `WHERE govt_id_number IS NOT NULL` useless for the question the front desk actually asks — _which of my patients have no Emirates ID?_ — because a passport-only tourist satisfies that predicate identically.

Making Emirates ID a row in the new collection instead was rejected for a different reason: **it is a singleton by law.** One person, at most one Emirates ID, ever. Putting a guaranteed-singleton into an unbounded collection erases that guarantee from the schema, and every consumer that needs _the_ Emirates ID then filters a list and handles a two-results case that cannot legally occur. The collection exists precisely because passports and visas _do_ legitimately repeat — a dual national holds two valid passports — and Emirates ID does not belong to that category.

Three consequences follow, and all three look like omissions without this record:

**Uniqueness is deliberately asymmetric.** `emiratesId` carries a partial unique index on `(tenantId, emiratesId) WHERE is_deleted = false AND emirates_id IS NOT NULL`; identity documents carry no uniqueness constraint at all. Two active Patients in one Tenant sharing an Emirates ID is never legitimate, so blocking it is correct — and useful, because the conflict tells the receptionist that the patient already has a chart rather than letting them open a second one. The number persists for life (renewal reissues the card, not the number), so there is no legitimate collision to accommodate. Identity documents are the opposite: passport numbers are only unique _within their issuing country_, so India and Brazil can both issue `J8369854`, and the previous index on `(tenantId, govtIdType, lower(govtIdNumber))` would have rejected the second patient as a duplicate. That index is dropped rather than fixed, because hard-blocking registration contradicts the Patient Reconciliation rule that matching "may identify candidates but never links or merges Patient records automatically." Document-based duplicate detection, if it is wanted, belongs in `findPotentialPatientMatches` as candidates — not in a constraint.

**The value is stored digit-normalised and the check digit is not validated.** The card is printed `784-1990-1234567-1`; the column stores `784199012345671`. Without normalisation the unique index is worthless, because three spellings of one ID all insert cleanly. Validation enforces fifteen digits and the `784` prefix — the UAE's ISO 3166-1 numeric country code — and stops there. The ICP has never officially published the Emirates ID check-digit algorithm; Luhn is what third-party implementations generally assume and it validates most real IDs, but not provably all of them across issuance eras. A false rejection here turns away a patient holding a valid card at a registration desk, which is a far worse outcome than accepting a typo that the unique index or a human will catch. If it is ever wanted, it belongs as a soft "this doesn't look right — continue?" warning, never as a hard validation error.

**The year segment is not cross-checked against `dateOfBirth`.** `YYYY` in the format is the birth year and the temptation to validate it is obvious. Real cards contain mismatches, and `patient.date_of_birth` is nullable anyway, so the check would reject valid data and pass over absent data.

Normalisation moves a problem to the read side that is easy to miss: patient search stores digits but receptionists type the dashed form off the card, so the search predicate normalises the query too, and only matches `emiratesId` when the query actually contains digits — an un-guarded strip turns a name search for `O'Brien` into an empty string that matches every patient in the Tenant.
