# Client Forms Use react-hook-form With a Dedicated Zod Schema

Interactive forms in the authenticated app (starting with the Role create/edit sheet) were built as hand-rolled controlled components: one `useState` per field, manual `validateDraft()` functions, and bespoke wiring to surface server errors. As screens multiplied this produced large, repetitive page components — the Roles page implementation alone grew past 900 lines — with validation logic and error handling reinvented each time. We are standardizing client forms on `react-hook-form` with `@hookform/resolvers` and a `zodResolver`. Each form gets its own client-side Zod schema co-located in the route's `_utils/` directory, and the submit handler maps validated form values to the module's API request type.

The schema deliberately is **not** the API Zod schema. The API schemas under `app/api/lib/modules/*/schemas/` are the server contract: they carry server-only concerns such as `.strict()`, value transforms (e.g. uppercasing a code), and null-versus-undefined normalization, and their messages are worded for API consumers. Pulling those into the UI would couple the client to API internals and surface server-worded messages to end users. A separate, UI-shaped form schema lets validation messages stay forgiving per `DESIGN.md`, keeps the form's value shape aligned with the inputs, and leaves the API schema free to evolve as the true contract. Forms run in `mode: 'onTouched'` so validation fires on blur rather than on every keystroke (the forgiving-forms rule in `DESIGN.md`), and server-side errors returned from a mutation are mapped back onto fields with `setError`.

The trade-off is two schemas describing overlapping shapes and a new runtime dependency on `react-hook-form`/`@hookform/resolvers`. We accept that duplication because the two schemas answer different questions — "is this input well-formed for a human filling a form" versus "is this payload a valid API request" — and conflating them has historically leaked server concerns into the UI.

This decision sets the convention for all future client forms, not just Roles. It is reversible in principle — react-hook-form is contained at the form-component boundary — but reversing it means rewriting every adopted form, so new screens should follow it rather than reintroduce hand-rolled controlled forms. The mechanical rules live in the "Screen composition" section of `CLAUDE.md`.
