# The Audit Log Is an Append-Only Event Table Written From Route Success Branches

A hospital has to be able to answer "who opened this Patient's record?" and "who changed this signed note, and from what?" The EMR records this as **Audit Events** in one table, `audit_event`, read through the Audit Log pages (All Audit Events and User Audit Events) and their CSV and PDF exports. The Audit Log is distinct from Analytics Events (ADR 0050), which leave the system and carry no Patient data, and from Timeline Events (ADR 0041), which are derived from business columns and carry no actor or before/after.

**One append-only table, an exception to soft delete.** An Audit Event has no `isDeleted`, no `modifiedOn`, and a `BEFORE UPDATE OR DELETE` row trigger raises on any change, so not even application code can rewrite or remove one. This is the named exception to ADR 0012: soft-deleting an audit record would defeat it. `patientId` and `visitId` are plain integers, not foreign keys, so the trail never blocks removing the records it describes. The actor's name and email are snapshots, so renaming a user never rewrites history. Each event carries the Tenant, and every read filters by it; the Patient join is Tenant-qualified too.

**Actions come from one catalogue.** Every event names an action from `audit-action-catalogue.ts` (`visit.amend`, `patient.view`, `audit-log.export`, …). The category (`access`, `create`, `update`, `delete`, `export`, `admin`) and entity type are derived from the action by the validator, never supplied by the caller, so an action is always filed where the catalogue says. Adding an action is one reviewed line.

**Module and Operation are derived, Roles are a snapshot.** Each catalogue entry also names its Module (Visits, Patients, Billing, Identity & Access, Audit Log) and Operation (View, Create, Update, Amend, Delete, Sign, Status change, Assign, Revoke, Export), the two labels competing HMS audit screens lead with. They are derived from the action when read, not stored, so regrouping an action relabels its whole history consistently, and filtering by them becomes a filter on the matching actions. Everything recorded inside a Visit (Clinical Notes, Vital Signs, Visit Diagnoses, Visit Documents) belongs to the Visits Module. The actor's Roles, by contrast, are stored with the event (migration 0082): who someone was when they acted must not change when their Roles later do.

**Recorded from the route's success branch, awaited, never failing the response.** `recordAuditEvent(tenantSession, request, action, details)` takes the actor from the Session and the IP address and user agent from headers, never from the body, and an impersonated Session records the real operator as `metadata.impersonatedBy` so support access is visible to the Tenant. It is awaited, so the event is written before the response leaves a serverless function. A failure to record is logged and swallowed: the action has already committed, and failing the response would invite a retry that repeats it.

The event is **not** written in the same database transaction as the change. Repositories each use the shared `db` handle and no transaction is passed between them, so making every command transactional with its audit row would mean threading a transaction through every repository. That cost is not paid in v1. The consequence is a small window in which a change can commit and its Audit Event fail to write; the failure is logged. If a regulator or customer requires transactional capture, the migration path is to give repository writes an optional transaction argument and move recording into the command, inside that transaction.

**Before and after are compared on listed fields only.** For updates and amendments the route reads the record with the module's existing get-by-id query before calling the command, and `diffAuditFields(before, after, FIELDS)` stores `{ field, label, from, to }` for each listed field that changed. Nested summaries are compared by what a person reads (`doctor.name`), long values are cut at 10,000 characters, and a field not on the list is never recorded. Lists such as Visit Diagnoses record `{ added, removed }` codes in `metadata` instead. This supersedes the gap ADR 0047 recorded, where an amended signed Clinical Note kept only its latest amender: the Audit Log now keeps every amendment with its before and after.

**What is recorded.** Opening a Patient, a Visit and the Consolidated Patient Report; every Visit lifecycle step and amendment; creating, changing, signing, amending and deleting Clinical Notes and Vital Signs; saving and amending Visit Diagnoses; adding and deleting Visit Documents; Patient registration, update, deactivation and deletion; finalizing and voiding Invoices and recording Payments; Role, Role permission and Staff changes; and exporting the Audit Log. List and search screens are not recorded row by row, and reading the Audit Log is not recorded (it would fill the log its reader is looking at); exporting it is.

**Access and export.** `audit-log:read` lists the Audit Log; exporting also needs `audit-log:export`, because data leaving the system is the riskier act. Both are granted to the system Tenant Admin role. The export is a synchronous CSV of at most 50,000 events, laid out the way hospital audit reviewers expect: one row per changed field with Field, Old value and New value columns, tied together by an Event ID, and the date and time in the Tenant's time zone beside UTC. The table on the Audit Log page shows the same columns, stacking each event's changed fields so their old and new values line up. A larger selection is refused with 422 rather than truncated, because a partial audit export reads as a complete one. Every Audit Log export (All Audit Events, the User Audit list and one user's audit) also comes as a PDF: a branded landscape A4 report built on the server with jsPDF, like the appointment schedule, headed with the Tenant, period, count, who exported it and when, and the filters in words, and footed as confidential on every page. A PDF holds at most 5,000 Audit Events (the 422 points to CSV) and up to 8 changed fields per event; the CSV stays the complete record. PDF text is set in Noto Sans, with Arabic runs in Noto Sans Arabic (both SIL Open Font License, kept in `app/api/lib/export/fonts`), so Arabic names print joined and right to left, even inside a cell that mixes scripts; jsPDF embeds only the glyphs used. A script neither font covers, such as Devanagari, prints as "?", and the CSV keeps every name exactly. User Audit exports are recorded as `user-audit.list-export` and `user-audit.export`, the latter naming whose audit left the system. Cells a spreadsheet would run as a formula are prefixed with an apostrophe, and the export is itself an Audit Event carrying its filters and row count. From and To are the Tenant's local days, converted to instants in SQL so the `(tenant_id, occurred_on)` index is used.

**Sign-in and Sessions are recorded too, and User Audit reads them.** The sign-in route records `auth.sign-in` with the id of the Session it created (looked up from the token, which is never stored); a refused password or blocked account records `auth.sign-in-failed` with outcome `failed` in each Tenant of the user the email names, and an email that names no one is not recorded, since there is no Tenant to file it in. A failed sign-in is recorded after the response is sent, so a refusal takes the same time whether or not the email names someone, and at most 10 are recorded per user per Tenant in any 15 minutes, so a loop of wrong passwords cannot grow the table without bound. Sign-out records `auth.sign-out` with why the browser ended the Session (the `trigger` query parameter: the user, a stale tab, expiry, or unavailable storage); ending one's own other Sessions records `auth.session-revoke`, and an admin's `user.sessions-revoke` lists the Session ids it ended. Every Audit Event also stores the Session id it was recorded in (migration 0083), so a Session's sign-in, actions and end read together. BetterAuth deletes a Session row when it ends, so this history exists only in the Audit Log. The User Audit pages (`/audit-log/users`) piece each user's Sessions together from those events and the live Session store: signed out (with the reason), ended by an admin or from another Session, expired without signing out, or still active. Sessions that began before tracking show as active with their sign-in unrecorded. Signup signs the new Tenant Owner in, so the signup route records that first Session as an `auth.sign-in` too, with `signup: true` in its metadata.

**Deliberately left for later.** A hash chain for tamper evidence, monthly partitions with cold archive, a retention period (a legal decision; UAE health-data law is commonly read as requiring at least 25 years), asynchronous exports, fonts for scripts other than Latin, Greek, Cyrillic and Arabic in PDF exports, streaming to a hospital's SIEM, FHIR `AuditEvent` output, failed-access (403) events, and Visit Document downloads, which are served directly from Blob storage and so never pass through the server.
