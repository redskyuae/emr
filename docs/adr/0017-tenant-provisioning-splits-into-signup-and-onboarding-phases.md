# Tenant Provisioning Splits into Signup and Onboarding Phases

Signup latency became unacceptable because Tenant Provisioning seeded the Permission Catalogue and all default Masters (appointment, asset, work order) inline before responding. We split provisioning into two phases: `POST /api/v1/signup` now creates only the Tenant Owner, the Tenant, and the active Tenant Session (still all-or-nothing with rollback), and a new session-scoped `POST /api/v1/onboarding` performs Tenant Onboarding — idempotently seeding the Permission Catalogue and default Masters, then stamping `onboardedAt` in the Tenant's metadata. This partially supersedes ADR-0006's requirement that provisioning be one all-or-nothing flow.

The partial-provisioning state ADR-0006 warned about (a Tenant with a Session but no baseline configuration) now exists transiently and is contained server-side: the protected app layout redirects any not-yet-onboarded Tenant to `/onboarding`, the onboarding page redirects already-onboarded Tenants to the dashboard, and the onboarding command returns success without re-seeding when `onboardedAt` is already set. The never-re-seed guard is a correctness requirement, not polish: seed inserts use `onConflictDoNothing` against partial unique indexes that exclude soft-deleted rows, so re-running seeding on an established Tenant would resurrect defaults a Tenant Admin deliberately deleted. Because onboarding seeding is itself not atomic, a failed attempt can leave some master families seeded and others empty, so the guard is evaluated per master family (appointment, asset, work order): a family counts as seeded only when every one of its tables holds at least one row for the Tenant, deleted or not. A retry therefore seeds only the families a previous attempt missed instead of stamping `onboardedAt` over missing defaults. Tenants provisioned before this change carry no `onboardedAt` flag but have every family fully populated, so when one reaches onboarding it only gets the flag stamped — established Tenants are never re-seeded. The Permission Catalogue upsert is global and idempotent, so onboarding always runs it.
