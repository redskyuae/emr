# Visit Status Is a Tenant Master With System Categories

A Visit moves through a lifecycle — a Patient checks in, waits, is seen, and the encounter ends — and `CONTEXT.md` needs a stable way to describe that lifecycle for both business rules and reporting. We considered a fixed, code-level enum (the approach taken for Patient's coded demographics, ADR 0020) against a Tenant-configurable Master, and chose the latter, following the precedent already set by Work Order Status.

VisitStatus is a Tenant-scoped Master: each Tenant gets its own rows and can rename them, recolor them, or add its own (e.g. a Tenant that wants a "Triage" status distinct from "Waiting"). Every VisitStatus carries a fixed **Visit Status Category** — `WAITING`, `IN_PROGRESS`, `COMPLETED`, or `CANCELLED` — and it is the category, not the individual status, that the Visit lifecycle's legal transitions and rules key off (a Visit may move from a WAITING-category status to an IN_PROGRESS-category status, but never the reverse). Four System Visit Statuses, one per category, are seeded at Tenant Onboarding with `isSystem: true`; their code and category are immutable, but Tenants may still edit their display name, description, and color, matching how System Work Order Status behaves.

The alternative — a fixed enum, as used for Patient gender or blood group — was rejected because a Visit's status is operational front-desk language that varies by Tenant ("Waiting" vs "In Queue" vs "Triage"), not a closed clinical fact like blood group. A closed enum also gives Tenants no way to add intermediate states without a code change, whereas the category indirection lets the code enforce lifecycle rules against a small, stable set while Tenants configure the labels they see day to day.

The trade-off is that every transition-related validator must resolve a status row to its category before checking a rule, rather than comparing an enum value directly — one extra join, mirrored from Work Order Status. This is accepted because it is the same shape already proven out in that module, and reversing it later would mean migrating every Tenant's existing Visit rows and custom statuses onto a new fixed set.
