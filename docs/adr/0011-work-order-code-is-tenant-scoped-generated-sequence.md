# Work Order Code Is a Tenant-Scoped, System-Generated Sequence

A Work Order is a maintenance job raised against an Asset, as recorded in `CONTEXT.md`. The maintenance screen and its mock data identify each Work Order by a short, human-facing code such as `WO-1042`, displayed in the queue and in the New Work Order sheet. We decided this code is **assigned by the server**, not entered by the user, and is a **monotonic sequence scoped to the Tenant** rendered as `WO-` followed by a zero-padded (minimum four digit) integer (e.g. `WO-1001`, `WO-1042`). Clients never send the code on create; the server allocates the next value for that Tenant and returns it. The code is unique per Tenant (case-insensitive), and the integer identity column remains the true primary key.

This **deliberately diverges** from the Asset entity decision (TASK-045), where we chose to have *no* human-facing code and to expose only the integer `id`. The divergence is intentional: a Work Order code is an operational reference that technicians and clinicians quote verbally and on paper ("close out WO-1042"), so a stable, friendly, per-Tenant identifier carries real workflow value, whereas an Asset is already identified by its physical `serialNumber`. Recording the decision here prevents a future reader from "fixing" the inconsistency by deleting the Work Order code or, conversely, retrofitting codes onto Assets.

The trade-off is generation complexity. A naive `MAX(sequence) + 1` read-then-insert races under concurrent creates within the same Tenant and can yield duplicate or skipped codes. The implementing task must allocate the next number **atomically per Tenant** — for example a dedicated per-Tenant counter row updated with `UPDATE ... RETURNING` inside the create transaction, or a transaction-scoped advisory lock keyed by Tenant — so two simultaneous creates cannot collide. Gaps are acceptable (a rolled-back create may consume a number); strict contiguity is not a requirement. Soft-deleted Work Orders retain their codes and their numbers are not reused. The per-Tenant uniqueness is additionally backed by a partial unique index on `(tenant_id, lower(code)) where is_deleted = false`, consistent with `lessons.md`, so any generation bug surfaces as a constraint violation rather than silent duplication.

This decision is reversible only at meaningful cost once Tenants accumulate Work Orders under the `WO-####` scheme, since the codes will already be in operational use; changing the format or scoping later would require a migration and would invalidate references staff have recorded outside the system.
