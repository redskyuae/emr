# Work Order Code Is a Tenant-Scoped, System-Generated Sequence

A Work Order is a maintenance job raised against an Asset, as recorded in `CONTEXT.md`. The maintenance screen and its mock data identify each Work Order by a short, human-facing code such as `WO-1042`, displayed in the queue and in the New Work Order sheet. We decided this code is **assigned by the server**, not entered by the user, and is a **monotonic sequence scoped to the Tenant** rendered as `WO-` followed by a zero-padded (minimum four digit) integer (e.g. `WO-1001`, `WO-1042`). Clients never send the code on create; the server allocates the next value for that Tenant and returns it. The code is unique per Tenant (case-insensitive), and the integer identity column remains the true primary key.

This **deliberately diverges** from the Asset entity decision (TASK-045), where we chose to have _no_ human-facing code and to expose only the integer `id`. The divergence is intentional: a Work Order code is an operational reference that technicians and clinicians quote verbally and on paper ("close out WO-1042"), so a stable, friendly, per-Tenant identifier carries real workflow value, whereas an Asset is already identified by its physical `serialNumber`. Recording the decision here prevents a future reader from "fixing" the inconsistency by deleting the Work Order code or, conversely, retrofitting codes onto Assets.

The trade-off is generation complexity. A naive `MAX(sequence) + 1` read-then-insert races under concurrent creates within the same Tenant and can yield duplicate or skipped codes. We use a dedicated `work_order_code_counter` row keyed by Tenant. Creating a Work Order atomically inserts or increments that Tenant's counter with `RETURNING` inside the same transaction as the Work Order insert; the first allocation is 1001. This keeps allocation explicit, avoids parsing existing codes or hashing Tenant identifiers for advisory locks, and ensures simultaneous creates cannot collide. Gaps are acceptable; strict contiguity is not a requirement. Soft-deleted Work Orders retain their codes and their numbers are never reused. The per-Tenant uniqueness is therefore backed by a full unique index on `(tenant_id, lower(code))`, including soft-deleted rows, so a reset, allocation bug, or non-application write cannot duplicate a historical operational reference.

This decision is reversible only at meaningful cost once Tenants accumulate Work Orders under the `WO-####` scheme, since the codes will already be in operational use; changing the format or scoping later would require a migration and would invalidate references staff have recorded outside the system.
