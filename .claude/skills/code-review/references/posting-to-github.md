# Posting the review to a pull request

The whole review goes up as **one** GitHub review with `event: "COMMENT"`, so
the author gets one notification and every finding sits on its line. Never
post findings as separate issue comments, and never use `APPROVE` or
`REQUEST_CHANGES`: approving is a human decision, and GitHub refuses either
event on your own PR.

## 1. Find the lines a comment can sit on

GitHub only accepts an inline comment on a line that is in the PR's diff:
an added line or a context line inside a hunk. Anchor against GitHub's own
diff, not a local one:

```bash
gh pr diff <n> --repo <owner>/<repo> > "<tmp>/pr-<n>.diff"
```

List the commentable new-side lines per file:

```bash
awk '
  /^diff --git/ { file = "" }
  /^\+\+\+ b\// { file = substr($0, 7); next }
  /^@@/ { split($3, a, ","); line = substr(a[1], 2) + 0; next }
  file == "" { next }
  /^-/ { next }
  /^[+ ]/ { print file ":" line; line++ }
' "<tmp>/pr-<n>.diff" > "<tmp>/pr-<n>.lines"
```

For each finding:

- If its `path:line` is in that list, it is an inline comment with
  `side: "RIGHT"`.
- If it spans lines, set `start_line` and `line` (both in the list, both in
  the same hunk) with `start_side` and `side` set to `"RIGHT"`.
- If it is about a deleted line, use `side: "LEFT"` with the line number in
  the old file.
- If it can't anchor (an unchanged file, a missing file such as a test or a
  `loader.tsx`, a whole-PR concern), put it in the review body under
  **Comments outside the diff**, with its `path:line` in bold.

## 2. Write each comment body

Exactly the format from SKILL.md Step 6:

````markdown
**Severity:** Must Fix

**Why:** `findAppointmentsForDoctor` filters by `doctorId` but not `tenantId`. Doctor ids are serial across Tenants, so a front-desk user in one Tenant sees another Tenant's Appointments for the same id.

**How to Fix:** Add the Tenant filter, as `findAppointmentById` does at line 42:

```suggestion
    .where(and(eq(appointmentTable.tenantId, tenantId), eq(appointmentTable.doctorId, doctorId)))
```
````

Suggestion blocks:

- A ` ```suggestion ` block **replaces** every line the comment covers
  (`start_line` to `line`) with the block's content. Write the full
  replacement lines with their original indentation, not a fragment.
- Use one only when the fix is confined to those lines. When the fix also
  needs an import, a new file or changes elsewhere, use a ` ```ts ` block and
  say where it goes.
- Never on `side: "LEFT"` lines.

## 3. Write the review body

```markdown
## Code review

Must Fix (2) · Chore (3) · Nit (1)

<One or two sentences: the overall read, what's solid, what blocks the merge.>

Checks run on <short-sha>: tsc ✓ · eslint ✓ · unit tests ✓ (34 passed). <Any check not run, and why.>

### Comments outside the diff

**`app/(protected)/billing/invoices/page.tsx`**

**Severity:** Must Fix

**Why:** ...

**How to Fix:** ...
```

Leave out the **Comments outside the diff** heading when there are none. No
sign-off, no "generated by" line, no AI attribution.

If nothing survived the review, post nothing inline and offer the engineer a
one-line body instead ("Reviewed at <short-sha>: no issues found."). Post it
only on their yes.

## 4. Build the request

Write the request to `<tmp>/pr-<n>-review.json` with the Write tool, so the
Markdown in the bodies is escaped correctly:

```json
{
  "commit_id": "<headRefOid>",
  "event": "COMMENT",
  "body": "## Code review\n\nMust Fix (1) · Chore (0) · Nit (0)\n\n...",
  "comments": [
    {
      "path": "app/api/lib/modules/appointment/repository/appointment-repository.ts",
      "line": 118,
      "side": "RIGHT",
      "body": "**Severity:** Must Fix\n\n**Why:** ...\n\n**How to Fix:** ..."
    },
    {
      "path": "app/(protected)/appointments/_components/appointments-page-impl.tsx",
      "start_line": 40,
      "start_side": "RIGHT",
      "line": 44,
      "side": "RIGHT",
      "body": "**Severity:** Chore\n\n**Why:** ...\n\n**How to Fix:** ..."
    }
  ]
}
```

`commit_id` must be the `headRefOid` you reviewed. Before posting, check the
PR hasn't moved:

```bash
gh pr view <n> --repo <owner>/<repo> --json headRefOid -q .headRefOid
```

If it has, say so: the new commits may fix or move what you found. Offer to
re-review, and don't post the stale review unless the engineer says to.

## 5. Post it

```bash
gh api --method POST "repos/<owner>/<repo>/pulls/<n>/reviews" --input "<tmp>/pr-<n>-review.json"
```

The response's `html_url` is the review's link. Give it to the engineer with
the count by severity.

If GitHub answers `422` with "Line could not be resolved" or "must be part of
the diff", one comment's anchor is wrong and nothing was posted. Find it
against `<tmp>/pr-<n>.lines`, move that finding to the review body, and post
again. Don't drop the finding.

If `gh` is missing or not signed in, say so, ask the engineer to run
`gh auth login`, and show the review in the terminal meanwhile.

## 6. Clean up

```bash
git worktree remove --force "<tmp>/pr-<n>"
git update-ref -d refs/code-review/pr-<n>
git update-ref -d refs/code-review/pr-<n>-base
```

Do this whether the review was posted, changed or abandoned.
